C. 技术设计上的遗漏/含糊点：
1. **checkpoint 的原子性**：每步写 JSON，如果进程在写到一半时挂掉，JSON 损坏，resume 会失败。没提写临时文件再 rename 的原子写策略。对"断点续跑"这个核心卖点来说，这是实质缺陷。
2. **条件路由返回未知键的处理**：router 返回 mapping 之外的键怎么办？计划没写（应抛 GraphError）。
3. **中断恢复的语义**：`interrupt_after` 的检查点存的是"下一步节点集"，resume 时从 next_nodes 继续跑，这个逻辑计划里有暗示但没写清楚 interrupt_before 的检查点语义（存 next_nodes=[该节点]，恢复时执行它）。另外 resume 带 state_update 时，是合并进 state 再跑，细节没写。
4. **状态不可 JSON 序列化的情况**：节点返回的 dict 里有不可序列化对象（如函数、自定义类实例）时 checkpoint 会崩。计划没提约束（要求 state 必须 JSON 可序列化）或降级策略。
5. **并行扇出串行执行 + reducer 合并顺序**：多个下一节点串行执行，每个都改 state，后面的节点看到的是前面节点改过的 state——这与 LangGraph 的超步模型语义不同（LangGraph 并行节点各自拿到同一份输入状态，最后合并）。计划只说"按注册顺序串行跑完"，没有说明状态语义是"链式可见"还是"各自快照后合并"。这是一个语义歧义，会在实现时造成分歧，也和 LangGraph 对照表声称的"同名语义"不符。

6. **条件边 + 检查点的循环场景**：max_steps 抛 GraphError 时，已完成步骤的检查点都在，但 run 状态是"失败"，list/resume 的行为没定义（resume 一个超限的 run 会立刻再抛错？）。
