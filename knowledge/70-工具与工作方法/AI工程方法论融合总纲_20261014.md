# AI 工程方法论融合总纲

> 引用边界：本总纲只做"职责分工与衔接"的说明，不重复三篇资产各自的正文细节；各职责的具体规则以对应条目为准。本稿给出的职责、边界与衔接判断，均可回到下列条目或计划文件核对；不把任何一篇的结论夸大成另一篇的结论。

## 一、三种职责总览

处理一个长期复杂的工程任务，实际是三件事，别混成一件事：

| 职责 | 回答的问题 | 载体/资产 | 状态真相落在哪 |
|---|---|---|---|
| **任务管理**（管事） | 任务拆多细、进度到哪、换了工具怎么续 | [complex-task-decompose skill](../../complex-task-decompose/SKILL.md)（文件外置任务树） | `任务树.md`（唯一进度真相） |
| **方案审查**（审方案） | 方案靠不靠谱、怎么防单模型确认偏见 | [多模型协作方法论](多模型协作方法论_20261014.md)（多模型并行讨论 + 红队评审） | 定稿方案文档 |
| **流程执行**（跑流程，任务树称"流程编排"） | 多步、有分支、要人工把关的流程怎么自动跑、崩了怎么续 | [MiniLangGraph 工作流引擎方法论](MiniLangGraph工作流引擎方法论_20261014.md)（状态图引擎） | 运行检查点 |

> 计划文件把第三项称"流程执行"、任务树称"流程编排"，指同一职责：把一条可重复的流程编排成图并可靠执行。

## 二、边界：各自不做什么（不混为一谈）

- **任务管理**：只负责拆解、进度外置、跨工具续接。它**不替你写方案内容**，也**不负责跑流程**；它是"账本与地图"，不是"干活的手"。
- **方案审查**：只负责产出方案、攻击方案。红队评审官**只评审不生成原始方案**、**不写优点**（防确认偏见），也**不跟踪执行进度**、不编排流程。
- **流程执行**：只负责单条流程内的编排、检查点与中断恢复。它**不做跨任务的进度真相**（那仍是任务树），**不审方案**；且引擎**不内置**自动重试、线程池并发、子图、知识库同步、git 提交/推送，也**不为外部 API 调用提供超时/并发/exactly-once 保障**——这些要么在节点内自写，要么用外部脚本编排（详见 MiniLangGraph 方法论的已知限制）。

三条边界的共同点：**谁的事归谁，别用一个工具硬扛另一层的活。**

## 三、衔接关系：三步怎么接上

一条主线把三者串起来：

```
多模型并行讨论(Ask) → 红队评审攻击 → 定稿方案
        │（定稿方案作为背景/目标/验收）
        ▼
任务树拆解(L1/L2叶) → 叶任务执行
        │（其中"多步+有分支+需人工把关+怕崩"的子流程）
        ▼
MiniLangGraph 编排成工作流跑(检查点/中断/resume) → 产物回填叶任务
        ▼
更新任务树进度 + 刷新进度看板
```

衔接的三个关键点：

1. **方案审查 → 任务管理**：红队收敛后的**定稿方案**是任务树拆解的输入（背景/目标/验收标准）；没定稿就开拆，容易边做边改、反复重跑。
2. **任务管理 → 流程执行**：任务树把任务拆成"单一输入/单一输出/可核对"的叶。**不是每个叶都要上工作流引擎**——一次性、线性、靠对话能推进的叶直接做即可；只有**重复出现、有分支、需人工审批网关、怕中断崩溃**的子流程，才值得用 MiniLangGraph 编排。
3. **流程执行 → 任务管理**：MiniLangGraph 跑完的产物/结论**回填**对应叶任务；**进度仍以任务树为唯一真相**，工作流引擎的检查点只负责"单条流程内"的恢复，不取代任务树。

> 状态外置是两者的共性，但**层次不同**：任务树外置"整个任务的进度"，MiniLangGraph 外置"单条流程的执行状态"；二者不重复、不竞争。

## 四、适用场景与选用条件

| 情况 | 用哪层 | 依据 |
|---|---|---|
| ≥3 步、或多输入文件、可能跨多轮/触发上下文压缩 | 任务树 | complex-task-decompose 触发条件 |
| 开工前要定方案、怕单模型偏见、重要项目 | 多模型讨论 + 红队（重要项目跑 2 轮） | 多模型协作方法论 |
| 重复出现、多分支、需人工审批网关、怕中断崩溃的**本地**流程 | MiniLangGraph 编排 | MiniLangGraph 方法论适用建议 |
| 需要自动重试 / 多线程并发 / 内置调外部服务 | 三者都**不直接满足**，需节点内自写或外部脚本编排 | MiniLangGraph 方法论已知限制 |
| 两步能做完的一次性任务 | 都别用，直接做 | complex-task-decompose 反向下限（防过度拆解/过度工程） |

## 五、工程质量在电气自动化主业怎么落地

本总纲的三种职责是**通用**工作方法；落到水泥/电气自动化主业时，工程质量的把关另有依据：

- AI 生成代码/配置的**检查清单、回归核对、测试化核对**（断言三段式 EXP/ACT/MSG、容差、人工基准+自动对比+统计三层验证），见 [GitHub电气自动化项目调研报告](GitHub电气自动化项目调研报告_20260914.md)。
- 多智能体编排的**工程化经验**（任务状态外置、单线收敛、写权限分区、阶段门禁、断点续作），见 [编排器-工作者模式调研报告](编排器-工作者模式调研报告_20260914.md)——它也是 complex-task-decompose skill 的主要改进来源。
- 典型衔接：DCS 设备调试核对、知识库入库这类"采集→分析→核对→人工确认→落库"的流程，可用 MiniLangGraph 编排；其中的核对质量，按 GitHub 电气自动化报告的检查清单与测试化方法把关；整体进度记在任务树。
