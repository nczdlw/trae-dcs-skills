## 0. 评审对象押注的结果（一句话复述）

V1 押注：用 .NET 8 + EF Core + SQLite + MCP + Blazor，把强绑 AutoCAD 2015 的 VB.NET 单机工具，重构为"CAD 可选、AI 可操作、约 26–38 人周"的新系统，产出仍是符合 Sinoma 标准的 DWG 图纸。

## 4. 六视角挑战

1. **怀疑的决策者（ROI/机会成本）**：如果目标只是"在 AutoCAD 2026 上继续出图"，把 LineJig+绘图工具壳用 2026 API 重写（约 4–6 人周，推断—需确认）就能保底。V1 没有评估这个最小替代方案就直接押 26–38 人周，重构可能过度投资。缺一个"为什么不只做插件迁移"的论证。
2. **一线执行者（隐藏工作量）**：四个大项不在任务树里——①自动布线引擎重写（B2，最重的图形业务）②DWG 自动比对工具（F3 前置）③BID属性编辑器 127KB 业务规则的等比迁移（43 属性位联动、字体缩放、设备类型联动）④打印管线（DWG_PRINT2015 的布局/打印机/份数逻辑）。按 V1 现有 L4/L6 估算，这四项足以再吃掉 6–10 人周。
3. **最终用户（解决真问题）**：日常最大痛点是"出图快、改图快、图面规整"。V1 把篇幅给了 AI/架构，恰恰着墨最少的是出图质量本身（自动布线规则、图面修整体验）——这是用户最终拿图纸交付施工的东西。
4. **竞争对手（如何被反制）**：替代品就是现状（AutoCAD 手动+Excel 台账）。若新系统出图质量不稳定、修图更繁琐，用户退回手动比切换成本低得多。切换成本必须低于旧流程的痛，否则必败。
5. **合规安全方（什么会变成事故）**：涉密红线不只挡 Autodesk 云 API（V1 已挡），还要挡"AI 客户端→云端大模型"通道；AuditLog 记 Command 层，但 AI 侧对话记录不受本系统控制——需要在制度与文档里写明"仅限本地模型"。
6. **数据现实主义者（哪个数字承担全部论证）**：整个立项压在两个最脆的数字上——U2（无头可行性，未实测）和 26–38 人周（未做 WBS，V1 自认粗估）。决策最需要的两个数字恰好是证据最弱的两个。

## 5. 事前验尸（假设 12 个月后项目已失败）

**叙事一（技术死锁）**：spike 发现 Core Console 拒载 net8 程序集 → 转 ODA 需商业授权被否 → 方案 C 纯托管写块/属性能力不足 → 项目卡在"出图"环节 6 个月 → 最后花 5 人周做了个 2026 插件保底出图，其余 20+ 人周投入归档。
根因：U2 无 Plan B 决策树（F1），且没有 MVP 分层，输了就全输。

**叙事二（迁移沼泽）**：L2 按原 §8.2 开发导入器，联调时发现旧 XML 没有 PRL_门 列（死代码），推倒重来；第二次按"9 连锁位+分号拆分"重写后，双跑比对又因无自动比对工具，300 张图人工比对拖 3 个月，"可解释差异"清单越滚越长，切换日永远定不下来；并行期老工具继续产 XML，数据分叉彻底无法收敛。
根因：数据基线错（F2）+ 验收不可操作（F3）。

**叙事三（AI 幻灭）**：MCP 上线后 AI 改动把 `C-101_RUN` 写成 `C101_RUN`，命名规则校验通过（拼合法但设备不存在），上到图纸后被现场发现 → 用户关闭 AI 写权限 → AI 接口沦为只读 → Command 层/审计层投资无法变现。
根因：校验器只查语法不查语义（信号引用完整性），且无 diff 工具快速复核（F4）。

## 8. 总评

V1 值得肯定的三点：工程方向（解耦、Command 层、渲染接口唯一、旧数据只进不出）判断正确；事实引用精度高于常见水平（30+ 处抽查仅个别 ±1 行）；风险表 U1–U9 的自我认知诚实。

但按红队标准，V1 在当前状态下**不具备直接开工条件**：第 2 章基线按代码量计约 40% 覆盖，两个最大业务文件恰好藏着数据模型与出图流程的真相；§2.5(2)/§8.2 建立在死代码上；两大决策数字（U2 可行性、人周估算）一个未实测、一个无 WBS。评审发现的 12 项问题中 10 项有明确修复动作（G1–G10），全部为"改文档"级成本，无需返工代码。**按 G1–G10 修出 V2 后，建议 V2 直接进入立项评审（此时评审决策点从 9 个收敛到真正的关键 3 个：D4 出图路线、D9 轻量边界、新增 D-MVP 分层）。**
