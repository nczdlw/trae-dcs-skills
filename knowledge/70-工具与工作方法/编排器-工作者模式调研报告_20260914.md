# 编排器-工作者模式调研报告（8来源）

> 调研目的：研究 GitHub 上"一个 Agent 作为编排器（Orchestrator）组织多个 Agent 分工协作"（Leader-Worker / 中心化编排）成熟开源项目，提炼可借鉴设计，改进 complex-task-decompose skill（文件外置任务树）。

## 一、LangGraph supervisor（langchain-ai/langgraph-supervisor）

- supervisor 无内置提示词，用户自定（团队成员名单 + 按领域路由规则）；官方推荐工具模式实现（"Break down user requests into appropriate tool calls and coordinate the results"）
- 拆解即工具调用：`create_handoff_tool()` 为每个 worker 生成 `transfer_to_<agent>` 工具，任务描述写在工具参数里
- output_mode 双粒度回传：`last_message`（只回结论）/ `full_history`（全消息）——编排器上下文只放结论级信息
- forward_message 原样转发 worker 末条消息，防转述失真
- **无死循环防护、无重试**（反面教材，选用框架时需自补）

## 二、AutoGen v0.4 / Magentic-One（源码核实）

核心类 `MagenticOneOrchestrator`（`python/packages/autogen-agentchat/src/autogen_agentchat/teams/_group_chat/_magentic_one/`）：

- **双循环**：outer loop（计划级：GATHER FACTS → CREATE PLAN → 广播 ledger 全文重置全员）+ inner loop（步骤级：每轮产 Progress Ledger JSON 选下一位执行者）
- **Task Ledger FACTS 四节**：GIVEN OR VERIFIED FACTS / FACTS TO LOOK UP（须注明去哪查）/ FACTS TO DERIVE / EDUCATED GUESSES
- **Progress Ledger 五键**（各带 reason）：is_request_satisfied / is_in_loop / is_progress_being_made / next_speaker / instruction_or_question
- **stall 计数器**：无进展 +1、有进展 -1（可恢复），连续 ≥3 强制重入 outer loop 重规划；v0.4.4 更有 max_replans=3 上限
- **重规划仪式**：FACTS_UPDATE（猜测升级为已核实、必须新增至少一条新推测）→ PLAN_UPDATE（先写失败根因再出新计划，避免重蹈覆辙）
- ledger 状态全量可序列化（save_state/load_state）——状态外置可行性的工程证明

## 三、CrewAI Hierarchical（源码 lib/crewai/src/crewai/）

- manager 强制无工具、只委派（带工具直接 raise Exception）；委派描述原则："对方对任务一无所知，须交代你知道的一切，解释而非引用"
- **断点续作** `_get_execution_start_index()`：从第一个无产出（task.output is None）任务恢复，已完成只收集不重跑
- planning 模式计划要求：每步有 DONE 判据、**探索性查看不算完成、报错未恢复不算完成**、结尾 READY/NOT READY 门控
- expected_output 契约："MUST return the actual complete content, not a summary"；output_file 落盘
- 上下文超限自动五段摘要：任务概览/当前状态/重要发现/下一步/需保留上下文
- 死循环双保险：max_iter 超限 → force_final_answer 强制收尾；重复输入检测（"重用了相同输入，必须改试别的"）

## 四、claude-flow / Ruflo（v2.7.47 npm + v3 源码核实）

- **SPARC 五阶段**（Specification→Pseudocode→Architecture→Refinement→Completion），阶段间 **Quality Gate 显式清单门禁**（如"Specification Complete: 所有需求已文档化"）；编排器模板明确警告"过度拆解导致协调开销"
- 记忆 namespace+TTL 分层：artifacts(TTL=0 永久)/shared(1800s)/patterns(7天)/events(30天)
- **SessionRecord 快照**：跨会话打包 tasks+memory+agents 带统计（n 任务/m 记忆），新会话 hook 自动恢复、恢复结果可量化
- 任务状态机 pending|assigned|in_progress|completed|failed，状态变迁发领域事件（事件溯源）
- hook：任务完成自动 trainPatternsOnComplete 沉淀经验模式
- `.roo/` 目录为 v1 时代设计，当前版本无（v1 包超 150MB 无法核实，如实注明）

## 五、Anthropic 官方工程博客（两篇）

《How we built our multi-agent research system》(2025-06-13)、《Building effective agents》(2024-12-19)，anthropic.com/engineering。

### 1. 编排器职责与上下文管理
- LeadResearcher：分析查询→定策略→并行创建 subagent→综合结果→决定是否再研究（迭代循环），完成后交 CitationAgent 附加引用
- 其上下文只放：高层计划 + subagent 回传的压缩后发现，不含探索细节。核心原则"搜索的本质是压缩"：subagent 各自独立上下文窗口探索，把最重要 token 浓缩回传 lead
- 关键动作：lead 先把计划存入 Memory——因上下文超 20 万 token 会被截断
- 《Building effective agents》定义：orchestrator-workers = 中央 LLM 动态分解任务、委托 worker、综合结果；子任务不预定义，由编排器按输入动态决定

### 2. 任务分解机制
- 并行分解：一次并行启动 3-5 个 subagent（广度优先查询收益最大）；复杂查询耗时降 90%
- **努力度分级**（规则嵌入提示词）：简单事实查询 1 agent 调 3-10 次工具；比较类 2-4 个 subagent 各 10-15 次；复杂研究 10+ 个且职责明确
- 早期失败模式：简单查询 spawn 50 个 subagent、无止境搜索不存在的信源

### 3. 状态与进度存储
- 计划存 Memory（外部记忆），防 200k token 截断
- 长周期模式：每完成一个阶段先总结、把重要信息存外部存储再继续；上下文近上限时用干净上下文新开 subagent，靠"谨慎交接"保持连续性

### 4. subagent 提示词结构与输出契约
- **委托四要素**（与任务描述一体，防重复/遗漏）：objective（具体目标）、output format（输出格式）、工具与信源使用指南、清晰任务边界。模糊指令失败案例："research the semiconductor shortage" 导致 3 个 subagent 重复调查无分工

### 5. 验证与失败处理
- LLM-as-judge 按 rubric 打分：事实准确性、引用准确性、完整性、信源质量、工具效率
- 失败处理：不重启、从出错位置恢复（durable execution）；重试逻辑 + 定期检查点
- 并行失控防护：提示词内嵌努力度分级 + 明确 guardrails；评估最终状态而非逐轮路径

### 6. 对文件外置任务树的直接借鉴
1. 计划必须外置（印证"任务树文件是唯一进度真相"）
2. 阶段总结落盘 + 干净上下文交接
3. 工件系统防"电话游戏"：subagent 输出直接写文件系统，只回传轻量引用
4. 委托四要素 ≈ 叶任务字段检查清单
5. 努力度分级防过度投入
6. **单线收敛**：subagent 互相频繁更新会互相干扰，结果统一回 lead 综合——任务树应单写者

## 六、openai/swarm

无状态客户端循环（取 completion→执行工具→切换 Agent→更新 context_variables→无新调用则返回），仅 Agent 与 handoff 两个原语；已被 OpenAI Agents SDK 取代。

1. handoff = 函数返回另一个 Agent 对象，控制流即数据——"移交下一叶"可建模为返回下一叶编号
2. context_variables 跨 agent 共享状态——任务树即共享黑板
3. 函数出错把错误消息追加回对话让 agent 自恢复——对应叶任务"问题"字段 + 复查区：失败回写下轮自纠

## 七、BMAD-METHOD

敏捷角色 agent 团队两阶段交付（规划链 Analyst→PM→UX→Architect→PO，开发链 SM→Dev→QA），核心哲学 "**Stateless Agents, Stateful Documents**"（无状态智能体，有状态文档）。

- **story 文件结构**：描述、验收标准 AC、Tasks 复选框、Dev Notes、Dev Agent Record（Completion Notes/Debug Log/File List）、QA Results、Status 流转 Draft→Approved→InProgress→Done
- **checklist 机制**：实现且测试全过才许勾选；每任务后跑全量测试、禁谎报；Dev 只许改 story 指定 section（勾选框/记录区），不许改 AC
- devLoadAlwaysFiles 开工必读清单

借鉴：story ≈ 叶任务五要素超集（AC=核对、Tasks=状态、Dev Record=输出+问题）；**写权限分区**（执行者只改记录不改编排器定义的任务基准）；story 自带全部上下文对应"上下文自足"。

## 八、OpenHands

主 agent 通过专用委托动作把子任务交给专家 agent（CodeActAgent 用 AgentDelegateAction 委托 BrowsingAgent；新 SDK 用 TaskTool 按 subagent_type 调度，子代理独立上下文完成后回传）。

1. 子代理 Markdown+YAML frontmatter 文件化定义（name/description/tools/model）
2. skills 分项目级常驻（repo.md）与触发词条件加载——常驻最小信息 + 按需加载细节
3. 委派 = 独立子会话独立上下文、结果单线回主 agent

## 九、改进映射（对 complex-task-decompose skill）

调研产出 18 条改进点（IMP-1~18），采纳 13 条、不采纳 5 条（复杂度大于收益 / 已有等价机制 / 场景不适配）。已落实（SKILL.md 2026-09-14 版）：

| 采纳项 | 落实位置 | 来源 |
|--------|----------|------|
| 反向下限（防过度拆解） | 二、触发条件 | Anthropic 努度分级 + claude-flow |
| 阶段门禁（显式清单验收再进下阶段） | 三、拆解规则 | SPARC Quality Gate + CrewAI READY |
| 上下文自足检验法（单独贴新会话能做） | 三、准入标准4 | CrewAI 委派自包含 |
| 树头可选"已知事实"行 | 五、模板 | Magentic-One FACTS |
| 核对假完成排除（跑完没核对/看一眼/报错未恢复 ≠ ✅） | 五、模板说明 | CrewAI DONE 判据 |
| 产物防缩水（原文落盘不转述） | 六、检索目录 | Anthropic 工件系统 + CrewAI 契约 |
| 接续会话动作（读树→复述定位→确认续做） | 四、开工动作0 | claude-flow 快照 + 用户规则 |
| R3 自检三问（判据满足/重复劳动/下一步明确） | 八、R3 | Magentic-One Progress Ledger |
| R7 卡叶升级与重试上限（连续2轮无进展/重试3次→❌，重拆先写根因） | 八、R7 | Magentic-One stall + CrewAI max_iter |
| R8 写权限分区（只改状态/问题/进度行，改定义=走重拆） | 八、R8 | BMAD 写权限分区 |
| R9 单写者（子代理不写树不做 git，结果回传主会话） | 八、R9 | Anthropic 单线收敛 |
| 并行子代理小节（四要素指令：目标/输出格式/边界/禁止事项） | 九 | Anthropic 委托四要素 + OpenHands |

不采纳：五段式收尾摘要（进度行已覆盖）、事件溯源（git 已有审计）、FACTS 四节强制化（降为可选行）、LLM-as-judge（单 agent 无 judge 基础）、记忆 TTL 分层（文件体系已分层）。

## 十、实战教训（本次调研过程本身）

4 个并行调研子代理中 2 个发生越权：一个自行建了重复任务树并提前写入不完整入库条目；一个自行 git 提交。直接教训已固化进 skill：**R9 单写者 + 九节"禁止事项"要素**——给子代理的指令必须显式写明"只研究不落盘/禁止建树/禁止 git 操作"，不写就会靠猜。
