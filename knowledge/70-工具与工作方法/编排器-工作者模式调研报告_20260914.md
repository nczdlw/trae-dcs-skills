# 编排器-工作者模式调研报告（4来源）

## 一、来源1：Anthropic 官方工程博客（最重要）

两篇：《How we built our multi-agent research system》(2025-06-13)、《Building effective agents》(2024-12-19)，均见 anthropic.com/engineering。

### 1. 编排器职责与上下文管理
- LeadResearcher 职责：分析查询→定策略→并行创建 subagent→综合结果→决定是否再研究（迭代循环），完成后交 CitationAgent 附加引用。
- 其上下文只放：高层计划 + subagent 回传的压缩后发现，不含探索细节。核心原则"搜索的本质是压缩"：subagent 各自独立上下文窗口探索，把最重要 token 浓缩回传 lead。
- 关键动作：lead 先把计划存入 Memory——因上下文超 20 万 token 会被截断。
- 《Building effective agents》定义：orchestrator-workers = 中央 LLM 动态分解任务、委托 worker、综合结果；与并行化的区别在子任务不预定义，由编排器按输入动态决定（适合无法预测子任务的编码/搜索）。

### 2. 任务分解机制
- 并行分解：lead 一次并行启动 3-5 个 subagent（广度优先查询收益最大）；subagent 并行调 3+ 工具；复杂查询耗时降 90%。
- 努力度分级（规则嵌入提示词）：简单事实查询 1 个 agent 调 3-10 次工具；比较类 2-4 个 subagent 各 10-15 次；复杂研究 10+ 个且职责明确划分。
- 顺序控制：lead 同步等当前批次完成→综合→决定创建新 subagent 或调整策略；异步执行是已知瓶颈与未来方向。
- 早期失败模式：简单查询 spawn 50 个 subagent、无止境搜索不存在的信源。

### 3. 状态与进度存储
- 计划存 Memory（外部记忆），防 200k token 截断。
- 长周期模式：每完成一个阶段先总结、把重要信息存外部存储再继续；上下文近上限时用干净上下文新开 subagent，靠"谨慎交接"保持连续性。
- 进度更新方式即"lead 等批次→综合→再决策"的循环，subagent 完成后把发现回传 lead（单线）。

### 4. subagent 提示词结构与输出契约
委托四要素（与任务描述一体，防重复/遗漏）：objective（具体目标）、output format（输出格式）、工具与信源使用指南、清晰任务边界。模糊指令失败案例："research the semiconductor shortage" 导致 3 个 subagent 重复调查无分工。
- 思考引导：lead 用 extended thinking 规划（评估工具适配、复杂度、subagent 数量与各自角色）；subagent 在工具结果后用 interleaved thinking 评估质量、找差距、改下个查询（反思环）。
- 工具启发式：先看全部工具、匹配用户意图、专用工具优先。

### 5. 验证与失败处理
- LLM-as-judge 按 rubric 打分：事实准确性、引用准确性、完整性、信源质量、工具效率；单一 LLM 调用出 0.0-1.0 分+pass/fail 与人类判断最一致；20 条小样本起步。
- 人工评估补缺：发现 agent 偏好 SEO 内容农场而非权威学术 PDF（自动评估漏掉），后加信源质量启发式解决。
- 失败处理：不重启、从出错位置恢复（durable execution）；把工具故障告知 agent 令其自适应；AI 适应性+确定性保障（重试逻辑+定期检查点）；rainbow 部署渐进切流量。
- 并行失控防护：提示词内嵌努力度分级规则+明确 guardrails；评估最终状态而非逐轮路径。

### 6. 对"文件外置任务树"可借鉴设计
1. **计划必须外置**：lead 把计划写 Memory 防截断——直接印证"任务树文件是唯一进度真相，对话记忆只是缓存"。
2. **阶段总结落盘+干净上下文交接**：总结已完成阶段→存外部存储→上下文近上限时新会话读存储续做——对应每叶完成即写盘（R3）与跨会话接续"先读树、复述定位、确认后续做"。
3. **工件系统防"电话游戏"**：subagent 输出直接写文件系统，只回传轻量引用给协调器，防多级传递失真、省 token——对应叶任务"输出=产物文件路径"，复查按检索目录直达源头。
4. **委托四要素≈叶任务字段**：objective/output format/工具指南/边界 可映射到叶任务"输出/核对/输入/问题"，可作"上下文自足"的检查清单。
5. **努力度分级入提示词**：复杂度→并行数/工具调用预算的显式规则，防过度投入——建树时按复杂度定层数与叶数，简单任务不过度拆分（同文："只在简单方案不够时才加复杂度"）。
6. **单线收敛**：subagent 互相频繁更新会互相干扰（早期失败模式），结果统一回 lead 综合——任务树应单写者收敛，避免多 agent 并写一棵树。

## 二、来源2：openai/swarm（GitHub README）

**架构一句话**：无状态客户端循环（取 completion→执行工具→必要时切换 Agent→更新 context_variables→无新调用则返回），仅 Agent 与 handoff 两个原语；已被 OpenAI Agents SDK 取代。

可借鉴：
1. handoff=函数返回另一个 Agent 对象，控制流即数据，可被模型当工具调用——"移交下一叶"可建模为返回下一叶编号。
2. context_variables 作为跨 agent 共享状态在调用间存活——任务树文件即跨 agent 共享黑板。
3. 函数调用出错时把错误消息追加回对话让 agent 自恢复——对应叶任务"问题"字段+问题复查区：失败信息回写下轮自纠。

## 三、来源3：BMAD-METHOD（GitHub + docs.bmad-method.org）

**架构一句话**：敏捷角色 agent 团队按两阶段交付（规划链 Analyst→PM→UX→Architect→PO，开发链 SM→Dev→QA；v4 共 10 角色，v6 重构为 skills），核心哲学"Stateless Agents, Stateful Documents"（无状态智能体，有状态文档）。

要点：
- **story 文件结构**（SM 用 `*draft` 生成，存 docs/stories/）：描述、验收标准 AC、Tasks 复选框、Dev Notes、Dev Agent Record（Completion Notes/Debug Log/File List）、QA Results、Change Log、Status 流转 Draft→Approved→InProgress→Done。
- **checklist 机制**：实现且测试全过才许勾选任务框；每个任务后跑全量测试、禁止谎报测试通过；Dev 只允许改 story 的指定 section（勾选框/记录区），不许改 AC 等定义；QA review 以"全部测试过、File List 完整、Dev Agent Record 有记录、只改了允许的 section"为完成判据。
- Dev agent 原则："story 已含所需全部信息，除非明确指示不许再读其它文档"；另有 devLoadAlwaysFiles 开工必读清单。

可借鉴：
1. story 文件≈叶任务五要素超集：AC=核对、Tasks[]=状态、Dev Agent Record=输出+问题、Status 流转=状态机——与任务树同构，其"Status: Draft→Approved→InProgress→Done"四级状态机值得吸收。
2. 写权限分区：执行 agent 只改状态与记录字段，不重写任务定义——防执行者越权篡改基准。
3. "story 自带全部上下文 + 开工必读文件"——对应"每轮先读任务树"（R2）与叶任务"上下文自足"准入标准。

## 四、来源4：OpenHands（All-Hands-AI）

**架构一句话**：主 agent 通过专用委托动作把子任务交给专家 agent（ICLR2025 论文：CodeActAgent 用 AgentDelegateAction 把浏览委托给 BrowsingAgent；新 SDK 用 TaskTool 按 subagent_type 调度，子代理独立上下文完成后回传）。

可借鉴：
1. 子代理用 Markdown+YAML frontmatter 纯文件定义（name/description/tools/model），description 供编排器选人——工作者定义完全文件化。
2. skills（前身 microagents）分项目级常驻（repo.md）与触发词条件加载——对应检索目录：常驻最小信息+按需加载细节。
3. 委派=独立子会话独立上下文、结果单线回主 agent——与 Anthropic 单线汇报同型。
