# 复杂任务拆解（任务树 + 检索目录 + skill 收割）

## 一、为什么需要本流程

AI 执行复杂任务时，自动上下文压缩会把早期的关键任务信息裁掉，引发死循环：

**失忆**（忘了要求/进度）→ **重跑**（重做已完成的事）→ 对话更长 → 更快触发压缩 → 再失忆

根本原因：任务状态存放在对话记忆这个"易失性存储"里。

**破解原理：状态外置。** 任务拆解、进度、检索路径、问题记录全部写入磁盘文件。压缩机制裁得掉对话，裁不掉文件。**任务树文件是唯一进度真相，对话记忆只是缓存。**

## 二、触发条件（何时用）

满足任一条即使用本 skill：

1. 任务涉及 ≥3 个步骤，或 ≥2 个输入文件
2. 需要逐页 / 逐组 / 逐表批量处理
3. 会话可能跨多轮、中途可能触发压缩
4. 发现自己在重做之前做过的事（失忆信号，立即补建树）
5. 用户说"按任务树做 / 拆解任务"

已有对应任务类型 skill（如 interlock-analysis）时优先用那个，本 skill 是通用兜底。

**反向下限（防过度拆解）**：一条都不满足的简单任务直接做，不建树。拆解本身有协调开销——叶任务数要与交付物数量匹配，两步能做完的事不拆叶（借鉴 Anthropic 努力度分级：只在简单方案不够时才加复杂度；claude-flow 编排器模板同样警告"过度拆解导致协调开销"）。

## 三、拆解规则

### 层级（思维导图式）

| 层级 | 含义 | 划分依据 |
|------|------|----------|
| L0 根 | 复杂任务 | 一句话交付目标 |
| L1 阶段 | 里程碑 | 按交付物划分（不按时间） |
| L2 叶 | 简单任务 | 可独立执行的最小单元 |

**阶段门禁**：L1 阶段所有叶 ✅ 后，对照该阶段「交付物」做一次整体验收——显式过一遍判据清单，不是口头"看过了"——过关才进下一阶段（借鉴 claude-flow SPARC 的 Quality Gate、CrewAI planning 的 READY/NOT READY 门控）。

### 叶任务准入四标准（不满足任一条就继续往下拆）

1. **单一输入源**：一个文件 / 一个页码范围 / 一张表
2. **单一输出物**：一个文件或一节内容
3. **可独立核对**：有明确"对了"的判据
4. **上下文自足**：只靠检索目录 + 该叶产物就能复查，不依赖对话历史。叶内禁用"见上文/如前所述"式引用——检验法：把该叶单独贴给新会话能直接做（借鉴 CrewAI 委派原则："对方对任务一无所知，须交代一切，解释而非引用"）

## 四、开工动作

0. **接续会话（任务树已存在时）**：先读任务树 → 向用户复述定位（树头进度行：n/N、下一步叶编号、未决数）→ 经确认后续做下一叶，不重建树（配合 `templates\任务接续指令模板.md`；借鉴 claude-flow SessionRecord 快照恢复）
1. **先查经验知识库**：若本地存在 trae-dcs-skills 仓库（默认 `D:\trae-dcs-skills`），先读 `knowledge\INDEX.md`，按分类/标签定位同类任务经验，把相关条目登记进任务树的检索目录
2. 在工程目录 `AI任务管理\<任务名>\` 下创建 `任务树.md`（模板见下节）
3. 同目录生成 `任务树导图.svg`（规范见第七节）
4. 向用户展示树结构，确认拆解合理后再动手执行第一个叶任务

## 五、任务树模板（复制即用）

```markdown
# 任务树：<任务名>

> 目标: <一句话交付物>
> 唯一基准: <基准文件路径 + 版本>
> 本文件是唯一进度真相，对话记忆仅为缓存。每轮开始先读本文件。
> 状态图例: ⬜未开始 / 🔶进行中 / ✅完成已核对 / ❌有问题待复查
> 建树: <日期> | 最近更新: <日期> | 导图: 同目录 任务树导图.svg（每次更新同步重写）
> 当前进度: <n/N ✅｜下一步: <叶编号>｜未决: <数>（每完成一叶更新此行；会话收尾必核对并提交）
> 已知事实: <已核实的关键事实>（可选行，任务涉及大量待确认信息时用，如设定值/点表待核实——借鉴 Magentic-One FACTS 分区：已核实 / 待查 / 推测）

## L1-1 <阶段名>（交付物: <该阶段产出什么>）

- [ ] L1-1.1 <简单任务名>
  - 输入: <绝对路径 + 页码/工作表/行号>
  - 输出: <产物文件路径>
  - 核对: <怎么算对了>
  - 状态: ⬜
  - 问题: -

## L1-2 <阶段名>（交付物: <...>）

- [ ] L1-2.1 <简单任务名>
  - 输入: ...
  - 输出: ...
  - 核对: ...
  - 状态: ⬜
  - 问题: -

## 问题复查区

| 日期 | 叶编号 | 问题描述 | 按检索目录复查结果 | 结论 |
|------|--------|----------|--------------------|------|
```

说明：
- 叶任务编号 = 阶段.序号（如 L1-3.2），全树唯一；复查区、接续指令引用叶任务一律用编号
- 复选框勾选 = 该叶已执行完；「状态」字段 = 核对状态（✅ 才算真正关闭）。两者需保持一致
- 进度行 n/N 只计「状态 = ✅」的叶；只执行未核对的叶不计入——部分完成不算完成（汇报纪律：说做了 ≠ 做了）
- 颗粒度判据：AI 拿到该叶输入后能不提问直接完成；还要问 = 拆得不够，一个编号装多件事 = 拆得太细
- 颗粒度示例（正反例对照）：正例「提取图纸第 5-10 页连锁条件，产出该组条件表」——单一输入/单一产物/可核对，拆得刚好；反例「提取 A 组连锁并生成 B 组 VAR 表」——一个编号装两件事，必须拆成两个叶
- 「核对」判据要可判且排除假完成：跑完没核对不算 ✅、探索性看一眼不算 ✅、报错未恢复不算 ✅（借鉴 CrewAI planning 的 DONE 判据）

## 六、检索目录（每个叶任务必填）

| 要素 | 内容 | 作用 |
|------|------|------|
| 输入 | 源文件**绝对路径** + 精确定位 | 出问题后直达源头 |
| 输出 | 产物文件路径 | 复查时找到被检对象 |
| 核对 | 验证方法（抽查方式、比对基准） | 判断"对了"的客观标准 |
| 状态 | ⬜ / 🔶 / ✅ / ❌ | 恢复现场、定位断点 |

精确定位写法示例：

- `D:\项目\图纸\VP1260.pdf 第47页`
- `点号表.xlsx 工作表"DI" 第5-120行`
- `说明书.pdf §3.2 表4`

**产物防缩水**：叶任务产物必须原文落盘为文件；复查与后续引用一律读产物原文，不读、不写"转述版"（借鉴 Anthropic 工件系统防"电话游戏"、CrewAI expected_output 契约 "return the actual complete content, not a summary"）。

## 七、SVG 导图规范

- **位置与命名**：与任务树同目录，`任务树导图.svg`，浏览器直接打开
- **布局**：横向思维导图。左侧根节点（任务名 + 进度 n/N）→ 向右展开 L1 主分支 → L1 下挂 L2 叶节点
- **状态色块**（叶节点左侧小方块，一眼看全局进度和卡点）：

| 状态 | 颜色 |
|------|------|
| ⬜ 未开始 | 灰 `#9E9E9E` |
| 🔶 进行中 | 黄 `#F5A623` |
| ✅ 完成已核对 | 绿 `#34A853` |
| ❌ 有问题待复查 | 红 `#EA4335` |

- 图内只放任务名和状态，检索目录不进图（太长，看 .md）
- **同步规则**：每次任务树 .md 落盘时整体重写 SVG（SVG 是文本文件，不做增量修改）

## 八、执行规则（R1-R10，硬性要求）

- **R1 开工先建树**：复杂任务必须先产出任务树文件再动手，不允许边做边想
- **R2 每轮重读树**：每个子任务开始前重读任务树.md，以文件为准，不信对话回忆
- **R3 即时落盘**：每完成一个叶任务，先自检三问——①核对判据满足了吗 ②是否在重复劳动 ③下一步叶编号明确吗——再更新勾选、状态、树头进度行 + 保存产物 + 同步重写导图，绝不攒到最后（三问借鉴 Magentic-One Progress Ledger：完成/循环/进展判定）
- **R4 一次一叶**：一轮只处理一个叶任务，做完即写盘，保持单轮上下文小
- **R5 复查走目录**：出问题按检索目录直查源文件定位，再改
- **R6 跑通即收割**：全部叶 ✅ 且用户验收后，产出两样——任务类型流程提炼成 skill（见第十一节），任务产物 MD 经验入库 knowledge/（见第十一节"经验入库"）
- **R7 卡叶升级与重试上限**：同一叶连续 2 轮无实质进展，或单叶重试达 3 次，立即停——标 ❌ 进问题复查区、输出当前最佳结论并**升级用户决策**（说明卡点与已试方案），禁止静默自循环重试；重拆该叶前必须先写失败根因再出新拆法，防止原地打转（借鉴 Magentic-One stall 计数器与重规划仪式、CrewAI max_iter + force_final_answer 强制收尾、twincat-agent"有界重试→诊断模式→升级操作员"协议）
- **R8 写权限分区**：执行时只允许改勾选、「状态」「问题」字段和树头进度行；「输入/输出/核对」是任务定义，要改 = 走重拆（先记录原因再改），禁止静默改（借鉴 BMAD-METHOD：执行 agent 只改记录区，不许改验收标准）
- **R9 单写者**：任务树只由主会话（编排者）维护；子代理/并行会话不直接写树、不做 git 操作，结果一律回传主会话核对后统一落盘（借鉴 Anthropic 单线收敛：多写者互相更新会互相干扰）
- **R10 反模式拒绝清单**：AI 应主动拒绝并说明理由的请求/倾向（借鉴 plc-st-review BLUEPRINT "Anti-patterns to refuse"）：①未经用户确认做难以逆转的操作（强推、删基准文件、覆盖工程导出物）②跳过强制核对步骤（"直接提交，不用核了"）③添加用户没要求的"最佳实践"、与任务无关的改动和过度工程 ④为凑结果编造查证不到的数据/来源（违反信息边界）
- **R11 假设浮出水面**：叶任务执行中做了影响任务方向的假设，必须记入问题复查区并计入未决数，不得默默继续——推进性假设允许，但改变任务方向的假设必须明说上下文、假设内容、理由三件事（借鉴 Codex 假设管理红线：假设一旦导致任务偏离用户意图，必须显式标注）

## 九、并行子代理（编排者-工作者，可选）

叶任务量大且互不依赖时，可像多智能体系统的编排器一样并行派发子代理执行。本 skill 的主会话即编排者，子代理即工作者。

**适合并行**：调研类（多来源互不依赖）、批量同构（逐页/逐表/逐设备）、独立文件处理。
**不适合并行**：有依赖顺序的叶、要改同一产物的叶。

派发规则：

1. **子代理指令自包含四要素**：目标（做什么）、输出格式（返回什么结构）、范围边界（查哪些/只做什么）、禁止事项（明确"只研究不落盘"或指定唯一落盘路径，禁止建任务树、改主任务树、git 操作——见 R9）。子代理看不到主会话上下文，缺什么都会靠猜（借鉴 Anthropic 委托四要素：objective / output format / 工具指南 / 边界；实战教训：不写禁止事项，子代理会越权写树甚至自行提交）
2. **结果单线回收**：子代理返回后由主会话核对要点、统一写树，不在子代理侧更新任务树（R9 单写者）
3. **并行度克制**：2-5 个为宜，互不依赖才并行；调研类子代理要求注明来源（文件/类名/URL），查不到就写"未查到"，禁止编造

## 十、出问题后的复查流程

1. 读任务树「问题复查区」，定位出问题的叶任务
2. 按该叶「输入」直查源文件（精确到页码 / 工作表 / 行号）
3. 与该叶「输出」产物比对，定位差异
4. 修改后按该叶「核对」方法重新验证
5. 结论回写问题复查区表格

**禁止凭对话记忆直接改——必须先按检索目录回源头确认。**

## 十一、收割流程（任务类型跑通后）

### 跑通判定

所有叶任务 ✅ + 用户验收 + 问题复查区无未决问题。

### 收割步骤

1. 新建 `.trae/skills/<任务类型名>/SKILL.md`
2. 从跑通的任务树中提炼四样东西：
   - **分解模板**：L1 阶段 + 典型叶任务模式
   - **检索目录规律**：这类任务的源文件通常在哪
   - **核对方法**：每类叶怎么验证
   - **踩过的坑**：问题复查区里的教训
3. skill 正文底部放「变更记录」表：`| 日期 | 变更内容 | 来源任务 |`

### 同类套用（下次遇到同类任务）

调用该 skill → 复制其任务树模板 → 替换源文件路径 → 按叶执行。

### 异类加枝（遇到模板没有的部分）

在任务树上新增分支单独拆解 → 跑通后把新枝回写进 skill 对应小节，并在变更记录表记一行（日期 + 新增内容 + 来源任务）。

### 规则维护原则（防膨胀与基准验证，2026-09-14 新增）

- **优先约束而非新增**：规则集膨胀时，优先合并同类项、给现有规则加适用范围/类型参数，而不是新建规则类别——每多一个概念，使用方就多一个要学、要关、要调的负担（借鉴 plc-st-review "何时不要写新检查"）
- **基准案例集**：重要任务类型应沉淀一套人工审核过的基准案例（输入 → 期望产物）；此后 AI 产出一律与基准自动对比，通过率入统计表——**人工基准 + 自动对比 + 统计**三层验证（借鉴 Spec2Control fbd-baseline / evaluation-script / experiment_results 三层验证体系）

### 经验入库（R6 的第二产出）

1. 把任务产物 MD（规则 / 开发说明 / 实施说明 / 复核报告 / 数据表 / 方法论）复制到 trae-dcs-skills 仓库 `knowledge\` 对应分类（分类定义见 `knowledge\00-规范\分类规范.md`）
2. 按 `knowledge\00-规范\条目模板.md` 补 frontmatter（title/date/project/type/device/tags/summary/source），正文原样保留不改写
3. `knowledge\INDEX.md` 对应分类下加一行（一句话摘要取自 summary）
4. git 提交并推送

入库标准（TIL 原则）：**以后会再查的才入**。会话中间产物、一次性过程记录不入。
